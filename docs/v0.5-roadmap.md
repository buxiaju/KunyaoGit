# KunyaoGit v0.5 Roadmap

> 候选特性 + 优先级 + 详细规格。每个候选一页（动机 / 设计 / 风险 / 工作量）。
> 选择策略：v0.4 已经把"基础 Git + 命令面板 + 快捷键"做扎实，v0.5 自然延伸是**让命令面板能搜文件、让代码编辑能看到历史**。

---

## 0. v0.5 战略目标

1. **生产力工具化** — 从「能用」到「比命令行更顺手」
2. **填补关键空白** — Blame / 文件跳转是开发者每天用几十次的动作
3. **保持 v0.4 节奏** — 一个特性一个 commit + 完整测试

---

## 1. 【P0】`Ctrl+P` 快速跳转文件

### 动机

v0.4 命令面板只能搜**命令**（`Ctrl+Shift+P`），而 VS Code 用户最常按的是 `Ctrl+P`（跳转到文件）。v0.4 已经在 App.tsx 挂载了 `<CommandPalette />`，但缺**文件搜索模式**——v0.4 RELEASE_BODY 里已经预告过「v0.5 补」。

填补这个空缺后，命令面板的可用性会从「快捷键速查」升级为「模糊跳转器」。

### 设计

**快捷键**
- `Ctrl+P` 或 `Ctrl+E` → 打开命令面板的"文件搜索模式"
- `Ctrl+Shift+P` 仍走"命令搜索模式"（兼容 v0.4 习惯）

**UI**
复用 v0.4 的 `<CommandPalette />` 组件，加一个 `mode: 'command' | 'file'` 状态：
- 顶部 input 旁加 toggle：「命令 / 文件」
- 或：input 前缀符号自动识别（输入 `>` = 命令；输入 `:` = 行号；空 / 任意 = 文件）

**后端**
新增 `GIT_LS_FILES` IPC 通道（参数 `path`, `opts: { maxCount?, pattern? }`）：
```ts
// electron/services/git.ts
async listFiles(path: string, opts = {}): Promise<Result<{ path: string }[]>> {
  const r = await this.git.raw(['ls-files', '--others', '--exclude-standard', '-co', '--full-name'], { cwd: path });
  // 简单解析 + 去重
}
```
- 同时返回 tracked + untracked（开发中新建的文件）
- maxCount 默认 5000 防卡
- 前端用 fuse.js 或自己写的 50 行 fuzzy match

**跳转行为**
- 选中文件后：跳到 `RepoPage` 的「文件」tab 并自动展开到该文件（用 `useRepoStore.selectFileForEdit`）
- 文件名也支持中文路径

### 风险

- **大仓库（10k+ 文件）首次 `ls-files` 慢** — 加 maxCount 上限 + 异步加载
- **中文/特殊字符路径编码** — 测试用项目 KunyaoGit 自己（300+ 文件含中文注释）验证
- **untracked 文件爆炸** — `--others` + `--exclude-standard` 已经过滤 .gitignore，但临时文件可能漏进来

### 工作量

| 子任务 | 时间 |
| --- | --- |
| `GIT_LS_FILES` IPC + simple-git 解析 | 1h |
| `<CommandPalette />` 加 mode 状态 + toggle UI | 2h |
| Fuzzy 搜索算法（50 行） | 1h |
| `useShortcuts` 加 `Ctrl+P` | 0.5h |
| 跳转逻辑（`selectFileForEdit` + URL hash 同步） | 2h |
| i18n（toggle label / empty / error） | 1h |
| 测试：parseUnifiedDiff-style 单元 + CommandPalette 集成 | 2h |
| 文档 + commit | 1h |
| **合计** | **~10h（约 1.5 天）** |

## 2. 【P0】文件历史 + Blame

### 动机

开发者每天用几十次的两个动作：
- **Blame**：这一行谁改的 / 哪次 commit 引入的 bug
- **文件历史**：这个文件经历过的所有版本（特别是删了又重建的）

v0.4 已经做了 Cherry-pick / Revert，但**没有 Blame 入口**——v0.4 RELEASE_BODY 预告「文件历史 + Blame」是 v0.5 候选。

### 设计

#### 2.1 Blame（行内）

**触发**：编辑器打开文件后 → 左侧 gutter 鼠标悬停显示 commit hash + 作者 + 时间 + commit message（tooltip）；点击该 tooltip 跳到「该 commit 在 CommitHistory 的高亮行」

**后端**
新增 `GIT_BLAME` IPC 通道：
```ts
async blame(path: string, file: string): Promise<Result<{
  line: number;
  hash: string;
  author: string;
  date: string;
  message: string;
}[]>> { ... }
```
- 用 `git blame --line-porcelain` 解析（最稳的格式）
- 返回按行号排序的数组
- 缓存：以 (repo, file, commit) 为 key 存到内存，文件切换/刷新时失效

**UI**
- `src/components/repo/EditorPane.tsx`：在 Monaco 左侧加自定义装饰层（或用 `glyphMargin`）
- Hover 显示 tooltip（4 行：hash 短 + author + 相对时间 + message 第一行）
- 点击 hash 跳到历史 tab

#### 2.2 文件历史

**触发**：编辑器顶部工具栏加「📜 历史」按钮（紧挨着「保存」），点击展开侧边面板

**面板内容**
- 顶部：文件名 + 「X 次修改 · 当前在 Y」
- 列表：每次 commit 一行
  ```
  abc1234  2026-01-15  feat(login): 修复 token 过期
           me · 1 周前 · +12 -3
  ↓ 点击展开这次 commit 的 diff（与上一版对比）
  ```

**后端**
新增 `GIT_FILE_LOG` IPC 通道：
```ts
async fileLog(path: string, file: string, opts: { maxCount?: number; follow?: boolean } = {}): Promise<Result<CommitInfo[]>> {
  const args = ['log', '--follow', '--max-count', String(opts.maxCount || 50), '--format=%H|%h|%an|%ae|%cI|%s', '--', file];
  // 简单按 \| 解析
}
```

**UI**
- 新组件 `src/components/repo/FileHistoryPanel.tsx`
- 与 DiffViewer 复用 diff 渲染（`git diff <hash>~1 <hash> -- <file>`）

### 风险

- **大文件 Blame 慢**（如 lock 文件 5w 行）— 加行数阈值（> 3000 行不渲染 gutter hover，只显示「该文件过大」提示）
- **重命名 / 删除历史**（`--follow` 处理 90% 情况）— 检测到文件不存在时退化为 `git log --all -- <path>` 不带 `--follow`
- **gutter 实现选型** — Monaco `glyphMargin` / `decorations` 都行；先试 glyphMargin 实现 hover
- **冲突的 hover 区** — 不要遮住代码点击 / 行号点击

### 工作量

| 子任务 | 时间 |
| --- | --- |
| `GIT_BLAME` + 解析 | 2h |
| `GIT_FILE_LOG` + 解析 | 1h |
| EditorPane 集成 glyphMargin + tooltip | 4h |
| `FileHistoryPanel` 组件 + diff 复用 | 4h |
| i18n（hover tooltip / 面板标题 / 空状态） | 1.5h |
| 测试：blame 解析 / fileLog 解析 / 组件 | 3h |
| 文档 + commit | 1h |
| **合计** | **~16h（约 2 天）** |

## 3. 【P1】Worktree 管理

### 动机

VS Code / JetBrains 标配功能——同时多分支开发不互相污染。`git worktree` 是 Git 内置命令，但 CLI 用起来繁琐（路径要自己选、删的时候要小心）。

### 设计

**入口**：BranchPanel 顶部加「Worktree」tab（与「本地分支 / 远程分支」并列）

**后端**
新增 4 个 IPC 通道：
- `GIT_WORKTREE_LIST` — 列出所有 worktree
- `GIT_WORKTREE_ADD` — 新建（参数：分支、路径、baseBranch?）
- `GIT_WORKTREE_REMOVE` — 删除（参数：路径、force?）
- `GIT_WORKTREE_PRUNE` — 清理悬空 worktree

```ts
async worktreeList(path: string): Promise<Result<Worktree[]>> { ... }
async worktreeAdd(path: string, branch: string, worktreePath: string, baseBranch?: string): Promise<Result<void>> { ... }
async worktreeRemove(path: string, worktreePath: string, force = false): Promise<Result<void>> { ... }
```

**UI**
- 列表项：路径 + 当前分支 + 标记（当前 / 锁定 / 脏）
- 「+ 新建」按钮：弹窗选分支 + 路径
- 「删除」按钮：confirm 后调用 remove
- 双击 worktree 路径：在系统资源管理器中打开（用 `shellOpenPath`）

**类型**
```ts
export interface Worktree {
  path: string;       // 绝对路径
  head: string;       // 当前 commit hash
  branch: string;     // 当前分支
  isCurrent: boolean; // 是否是主 worktree
  isLocked: boolean;
  isPrunable: boolean;
}
```

### 风险

- **路径安全** — 拒绝 `..` 路径穿越；建议默认放 `<repo>/../<repo>-wt-<branch>`
- **Windows 路径长度限制**（260 字符 MAX_PATH）— 默认路径用 `<repo>\.wt\<branch>` 避免太长
- **删除脏 worktree** — 默认 force=false，脏时提示先 commit/stash

### 工作量

| 子任务 | 时间 |
| --- | --- |
| 4 个 IPC 通道 | 2h |
| Worktree 类型 + simple-git 解析 | 2h |
| `WorktreePanel` 组件 + 新建/删除弹窗 | 5h |
| BranchPanel tab 集成 | 1h |
| i18n | 1.5h |
| 测试：解析 / 组件 | 3h |
| 文档 + commit | 1h |
| **合计** | **~15h（约 2 天）** |

## 4. 【P1】Git 全局配置可视化

### 动机

设置页现在能配 GitHub / Gitee Token，但**应用内完全没法改 Git 全局配置**（`user.name` / `user.email` / `core.autocrlf` / `core.editor` / `pull.rebase` ...）。新手用户最常见的「Git 提交没作者名」就是配错了。

### 设计

**入口**：设置页加「Git 配置」tab

**后端**
新增 2 个 IPC 通道：
- `GIT_CONFIG_LIST` — 列出 (scope, key, value) 三元组
  - `git config --list --show-origin --show-scope`
- `GIT_CONFIG_SET` — 设置某 key（参数：scope: 'local'|'global'|'system', key, value）
  - `git config --{scope} {key} {value}`

**UI**
- 表格：三列（Scope / Key / Value）
- 按 scope 折叠：Local / Global / System
- 编辑：双击 Value 变成 input，回车保存
- 「+ 添加 key」按钮（仅 local scope）
- 「删除」按钮（仅非常规 key 需确认）

### 风险

- **scope 写错** — 严格 enum 校验
- **.gitconfig 损坏** — 写入前先 `git config --get` 验证；失败时 rollback
- **敏感 key**（如 `credential.helper`） — 写值时 warning，但允许
- **system scope** — Windows 上可能需要管理员权限；失败时给清晰提示

### 工作量

| 子任务 | 时间 |
| --- | --- |
| 2 个 IPC 通道 | 1h |
| 解析 `git config --list` 输出 | 1.5h |
| `GitConfigTable` 组件 + 内联编辑 | 4h |
| 设置页 tab 集成 | 1h |
| i18n | 1.5h |
| 测试：解析 / 组件 | 2h |
| 文档 + commit | 1h |
| **合计** | **~12h（约 1.5 天）** |

## 6. 推荐执行顺序

按"价值密度 / 实现难度 / 用户感知"打分（5 分制）：

| 候选 | 价值 | 难度 | 用户感知 | 推荐 |
| --- | --- | --- | --- | --- |
| **Ctrl+P 文件跳转** | 5 | 2 | 5 | 🥇 第一个做 |
| **文件历史 + Blame** | 5 | 3 | 5 | 🥈 第二个做 |
| **Worktree** | 3 | 2 | 4 | 🥉 视情况 |
| **Git 全局配置** | 3 | 1 | 3 | ⏸ v0.5+ |

**默认 v0.5 计划**：先做 `Ctrl+P` 文件跳转（1.5 天）→ 做文件历史 + Blame（2 天）→ 收尾 + 文档 + release。

**总周期估算**：3-4 天完成 v0.5 两个 P0 特性 + release。
